AI Orchestration Console

A local 3-stage coding pipeline,
driven by headless CLIs

One SQLite-backed run, one isolated git worktree, and three stage prompts — Plan (Claude Code), Execute (OpenCode), Review (Claude Code) — all invoked through a single NDJSON spawn helper that feeds the prompt over stdin and streams events out.

The run row in SQLite is the single source of truth. Every transition goes through setStatus, which writes the DB and emits an SSE event — the frontend never holds state the backend does not already have.

Status machine: planning → awaiting_approval → executing → reviewing → approved | needs_changes → closed_needs_changes · failed/cancelled from any point.

Why it matters Because approval is a real gate between Plan and Execute, the plan document gets human eyes before any code is written — and because Review is a separate fresh process, it judges only what is written down.

src/lib/cli/process.ts · the shared spawn helper

One function feeds a prompt and streams NDJSON

spawnAndStreamNdjson({
  command,    // "claude" | "opencode"
  args,       // per-stage flags
  cwd,        // the run's isolated worktree
  stdinText,  // the stage prompt
  onEvent,    // live-forwarded parsed events
})
// → { result: Promise<{ exitCode, events, stderr }>, kill(signal) }

The child is spawned with stdio: ["pipe", "pipe", "pipe"] — all three streams piped, no TTY anywhere:

const child = spawn(opts.command, opts.args, { cwd: opts.cwd, stdio: ["pipe", "pipe", "pipe"] });

if (opts.stdinText !== undefined) {
  child.stdin.write(opts.stdinText, "utf-8");
}
child.stdin.end();

The cwd is always the run’s disposable worktree — a stage process never sees the user’s main working directory.

process.ts · the design decision

Why the prompt goes over stdin, not argv

Plans and diffs are unbounded. A large plan, or a multi-megabyte cumulative diff fed to Review, is normal. argv is capped by the OS ARG_MAX (≈128 KB on Linux, ≈256 KB on macOS) — so passing the prompt as a command-line argument would make large runs fail at spawn time.

  • stdinText is written to child.stdin, then child.stdin.end() closes it — the CLI reads until EOF and runs once.
  • The prompt travels as a pipe, not a single argv string, so size is bounded only by memory.
  • Both CLIs read their instructions the same way, so the same helper serves all three stages.

The rule Feed the prompt over stdin, never argv — the pipeline is built on text of unbounded size.

process.ts · stdout parsing

The NDJSON line-buffer loop

const consumeLine = (line: string) => {
  if (!line.trim()) return;
  try {
    const parsed = JSON.parse(line) as NdjsonEvent;
    events.push(parsed);
    opts.onEvent(parsed);
  } catch {
    // Non-JSON stdout line (shouldn't happen with --format/--output-format json*); ignore.
  }
};

child.stdout.on("data", (chunk: Buffer) => {
  buffer += chunk.toString("utf-8");
  let idx: number;
  while ((idx = buffer.indexOf("\n")) >= 0) {
    consumeLine(buffer.slice(0, idx));
    buffer = buffer.slice(idx + 1);
  }
});

Output arrives in chunks, so lines are assembled across chunk boundaries. Each complete line is JSON.parsed into an NdjsonEvent; a non-JSON line is silently ignored rather than killing the stage.

A trailing partial line (no final newline) is flushed on close:

child.on("close", (code) => {
  if (buffer.trim()) consumeLine(buffer);
  resolve({ exitCode: code, events, stderr });
});

process.ts · stderr and the kill contract

stderr kept apart · SIGTERM first, SIGKILL after

stderr is accumulated separately and never mixed into the NDJSON stream, so stage diagnostics stay available even when stdout is clean:

child.stderr.on("data", (chunk: Buffer) => {
  stderr += chunk.toString("utf-8");
});

The handle returns { result, kill }: result resolves on close with { exitCode, events, stderr }; kill(signal) sends a signal to the live child.

Spec §6 contract kill sends SIGTERM first; the caller escalates to SIGKILL after a grace period. OpenCode exits 0 on SIGTERM — a “clean” exit in its own eyes — so cancellation is tracked by an explicit cancelled flag, never inferred from an exit code.

src/lib/orchestrator/prompts.ts · buildPlanPrompt

Plan: a rigid template, filled in

You are the Plan stage of an automated coding pipeline. Research this codebase (you cannot edit any files in this mode) and produce a plan for the following task.

Task: ${task}

Reply with ONLY the plan document below, filled in — no preamble, no commentary before or after it:

# <short task title>

## Objective
<one-line goal>

## Context
<relevant background/constraints found in the codebase>

## Steps
1. ...
2. ...

## Acceptance criteria
- <conditions that define "done">

## Out of scope
- <things this run must NOT touch>

Why it’s worded this way The fixed skeleton makes the reply machine-parsable — the backend extracts the final result event text verbatim — and human-approvable: the approval gate shows exactly one Objective, one Context, one Step list, one Acceptance-criteria list, one Out-of-scope list. “No preamble, no commentary” guarantees nothing precedes the document.

prompts.ts · buildExecutePrompt

Execute: the plan, as-is — and the retry branch

Implement the following plan exactly as written. Do not go beyond its "Out of scope" section.

${planText}

With reviewer feedback from a rejected attempt, the prompt becomes:

Implement the following plan exactly as written. Do not go beyond its "Out of scope" section.

${planText}

A reviewer already looked at your previous attempt and found issues. Address this feedback:

${retryFeedback}

Why it’s worded this way “Do not go beyond its Out of scope section” bounds Execute’s autonomy — the plan’s contents are passed as-is (buildExecutePrompt(planText, retryFeedback?)). On retry the reviewer’s feedback is appended verbatim — Execute never re-derives it from the diff, and can’t miss it.

prompts.ts · buildReviewPrompt

Review: judge only what is written below

You are the Review stage of an automated coding pipeline. You were not part of the planning discussion — judge only what is written below.

Here is the plan that was approved:

${planText}

Here is the git diff of the changes that were made:

${diffText || "(no changes were made)"}

Check the diff against the plan's "Acceptance criteria" section. Reply with your verdict as the very first line, exactly one of:

VERDICT: APPROVE
VERDICT: NEEDS_CHANGES

Then give your reasoning on the following lines.

Why it’s worded this way Review must not re-litigate the discussion it never saw — it is told explicitly it was not part of it. The plan and the diff are placed inline in the prompt, so Review checks what is actually written rather than exploring on its own. An empty diff renders as (no changes were made), and the verdict must be the very first line — that is what makes it machine-parseable.

Plan stage · src/lib/cli/claude.ts

Plan cannot write files — so the backend does

const args = ["--print", "--output-format", "stream-json", "--verbose"];
if (opts.mode === "plan") {
  args.push("--permission-mode", "plan");
} else {
  args.push("--allowedTools", "Read Grep Glob");
}

Plan runs with --permission-mode plan: Claude Code itself refuses any file write in this mode. That is enforced by Claude Code, not by an allowlist the stage could bypass — Plan is genuinely read-only by construction.

Because Claude cannot write the plan file, the backend captures the final type:"result" event’s text and writes it itself: writePlanFileAndCommit(worktree, finalPlanText) in pipeline.ts (≈:203). The commit becomes the first commit on the run branch, so the plan travels with the diff Review later checks against it.

Why this shape Researching is inherently file-heavy, but the plan is a single deliverable. Enforce read-only in Claude Code, extract the one artifact over NDJSON, and let the pipeline (not the model) own writing and committing it.

Review stage · claude.ts

Fresh, read-only, verdict-first — fail closed

args.push("--allowedTools", "Read Grep Glob");
  • Fresh session — Review never resumes Plan’s session, so it carries no reasoning it was told not to rely on.
  • Read-only — --allowedTools "Read Grep Glob": no Edit, no Write, no Bash. Review can inspect but never mutate.
  • Fed, not exploratory — the plan text and the diff are in the prompt, not discovered by wandering the repo.
export function parseVerdict(resultText: string): { verdict: "APPROVE" | "NEEDS_CHANGES"; reasoning: string } {
  const match = resultText.match(/^\s*VERDICT:\s*(APPROVE|NEEDS_CHANGES)\s*\n?([\s\S]*)$/);
  if (!match) {
    // Defensive default — treat an unparseable reply as needing a human look, never a silent pass.
    return { verdict: "NEEDS_CHANGES", reasoning: `Review reply had no parseable VERDICT line:\n\n${resultText}` };
  }
  return { verdict: match[1] as "APPROVE" | "NEEDS_CHANGES", reasoning: (match[2] ?? "").trim() };
}

Why fail-closed The regex anchors the verdict to the very first line. Anything unparseable — a truncated reply, a wrong token, a model tantrum — defaults to NEEDS_CHANGES, never a silent pass. A broken Review can only slow the pipeline down, not approve garbage.

Execute stage · src/lib/cli/opencode.ts

Execute: skip-permissions, or hang to timeout

const args = [
  "run",
  "--format",
  "json",
  "--model",
  opts.model,
  "--dir",
  opts.cwd,
  "--dangerously-skip-permissions",
];

--dangerously-skip-permissions is required, not optional: OpenCode’s default tool-permission flow expects an interactive prompt, and this process has no TTY to answer one. Without the flag, every Execute run would hang until the stage timeout killed it.

  • The blast radius is bounded: --dir points at the run’s disposable worktree, never the user’s main directory.
  • OpenCode reports its own failures as an NDJSON {"type":"error"} event on stdout — stderr is empty on those failures. describeOpenCodeError prefers that event’s detail.
  • Text is assembled from type:"text" parts; tokens and cost are summed across step_finish parts.

Isolation · src/lib/git.ts

Every run gets its own worktree

createRunWorktree gives each run an isolated git worktree, never an in-place branch checkout — the pipeline can’t disturb whatever the user has open in an editor.

  • computeDiff runs git add -A before diffing — plain git diff silently omits brand-new untracked files, so a file Execute created from scratch would otherwise be invisible to Review.
  • computeDiff always diffs against plan_commit_sha, never a moving HEAD — a retry’s diff shows the full cumulative change Review must check, not just the latest incremental edit.
  • commitExecuteChanges runs before any terminal state: removeRunWorktree deletes the worktree directory outright, so uncommitted Execute edits would be gone, not hidden.
  • No auto-merge, ever — a reviewed branch is left for the user to merge through their own git workflow.

History · src/lib/db.ts

SQLite, via the Node built-in

The data layer uses Node’s built-in node:sqlite (DatabaseSync) — the native better-sqlite3 module failed to compile against this machine’s Node version, and the built-in avoids native compilation entirely.

  • Schema changes go through addColumnIfMissing — a minimal ALTER TABLE migration — rather than dropping and recreating the table, because real run history must survive schema changes.
  • One DB file is shared by the web server and the orch CLI (5s busy_timeout), with the run row as the single source of truth.
  • Configure via ORCHESTRATOR_DB_PATH, defaulting to ~/.orchestrator/history.db.

Streaming · events.ts · control.ts

SSE, and the globalThis requirement

setStatus writes the DB row and then emits an SSE event; the frontend re-fetches the run over plain HTTP whenever a status_change arrives, and live logs are forwarded cli_event payloads.

Both events.ts (in-memory pub-sub) and control.ts (live child-process tracking) stash their module state on globalThis — not in a plain module-level variable.

Why globalThis Next.js dev-mode hot-reload can re-evaluate a file’s top level independently per route, so the route that starts a run and the route that later subscribes to its SSE stream don’t reliably share the same module instance. A plain const emitters = new Map() silently fragments into separate Maps that never see each other’s writes. Any new run-scoped in-memory state needs the same stashing pattern.

Control · src/lib/orchestrator/pipeline.ts

The approval gate and the retry loop

  • Gate: after Plan, the run parks at awaiting_approval. approveRun is the status guard and nothing else; the work lives in module-private approvePlan. The auto-approve chain in startRun calls approvePlan directly — parking at the gate first would publish an approve button the run doesn’t have.
  • Retry loop: needs_changes → retryExecute → executing → reviewing. The reviewer’s feedback is passed verbatim into the next Execute prompt.
  • Ownership: each run records owner_pid, so cancelRun can tell a run stranded by a dead process (close it out) from one a live process drives (refuse — finalizing deletes worktrees, and doing that under someone else’s Execute destroys uncommitted work).
  • No double-execute: approveRun, rejectRun, retryExecute and closeRun each refuse a run whose status has moved, so two processes at one gate cannot start two Execute stages on one worktree.

The CLI · src/cli/

orch: a second consumer, not a reimplementation

The orch CLI runs the exact same pipeline.ts state machine — every status transition still goes through the shared code, so the two interfaces cannot drift.

  • It runs the pipeline in the foreground in one process, so it subscribes to subscribeRunEvents directly instead of over SSE.
  • Ctrl-C awaits the outstanding pipeline promise before exiting — exiting the moment cancelRun returns could beat the cancelled status write and the worktree removal.
  • The same DB, the same worktree mechanics, the same three prompts — just a different front door.

Recorded, not fixed

Known gaps

  • One pipeline at a time is not enforced: SPEC.md:17 says it, but the CLI’s check is advisory and the web route has none.
  • Retry cap is off by one: retry_count starts at 0 and retryExecute rejects at >= 3, allowing four Execute↔Review cycles where SPEC.md:99 says three.
  • Cancellation window: a cancel landing in the window before a stage is registered still orphans that stage’s child process.
  • Error typing: the reject/close routes catch every error from rejectRun/closeRun as a 409 — only the status-guard throw is a refusal.

These are deliberate trade-offs at branch end, documented rather than swept under the rug.

The shape of the system

Everything reduces to a few invariants

  • Every stage is a headless CLI over a pipe — prompt on stdin, NDJSON on stdout, stderr kept apart, { result, kill } out.
  • Every transition is a DB row + an SSE event — the SQLite row is the truth; the UI just reflects it.
  • Every run is an isolated worktree — blast radius bounded, nothing leaks into the user’s checkout, nothing auto-merges.
  • Failure closes toward a human — unparseable verdicts become NEEDS_CHANGES; stranded runs can be closed out; gates refuse moved statuses.
